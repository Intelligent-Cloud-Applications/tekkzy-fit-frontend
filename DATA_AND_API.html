B. payment (prod) / beta_payment (dev)

Keys: PK cognitoId, SK paymentId. GSI: institution-paymentDate-index (institution, paymentDate). Access: Query by cognitoId, or Query the GSI by institution. Scan is only a fallback if that GSI is missing.

Fields: institution, memberId, client/userName, phone, amount, netAmount, feeAmount, currency, planId, planName, durationDays, paymentType, paymentMode (CASH / UPI / RAZORPAY), paymentStatus, status, razorpayPaymentId, razorpaySubscriptionId, razorpayPaymentLinkId, paymentLinkUrl, joinDate, startDate, renewDate, paymentDate, createdAt, createdAtIso, notes, isVerified

C. institute_product / beta_institute_product

Keys: PK institution, SK productId. Query, GetItem, PutItem, DeleteItem. No Scan in API.

Plan fields: name/heading, price (rupees), amount (paise), addonAmount, durationDays, durationLabel, billingPeriod, billingInterval, razorpayPlanId, description, accessType, status, createdAt, updatedAt

D. monthly_report / beta_monthly_report

Keys: PK institution, SK cognitoIdAndMonth (example: September-2026). Query, GetItem, PutItem. No Scan.

Snapshot: totalAttendance, totalMembers, cashPayment, upiPayment, razorpayPayment, totalDiscontinued, deletedAttendance[] (archived punches), reimbursements[], incomes, updatedAt

E. code_generator_variables / beta_*

Keys: PK institutionid, SK index ("0"). GetItem / PutItem only. One row per gym.

Gym settings: companyName, legalName, phone, email, address, city, state, pincode, gstin, reminderDays, timezone, currency, gateUnlockDurationSeconds, duplicateScanCooldownSeconds, allowExpired, allowSuspended, unknownFacePolicy, offlineModeEnabled

F. AWS Cognito user pool (us-east-2)

Staff emails, passwords, and roles (admin / manager). Not member data.

G. Razorpay

Subscriptions, hosted pay links, plans, webhooks. Cloud writes IDs back onto user_profile and payment.

H. Face machine (CardM / AI806) — not in DynamoDB

Users, faces, fingerprints, valid-until (endtime), punch logs. Phone app: POST http://{ip}/api. Website used a gym-PC helper that stored commands in user_profile.

I. Phone / browser only — not in DynamoDB

IndexedDB / AsyncStorage: last device IP, queued device users, extra attendance from the terminal, hidden/deleted punches. GET /attendance is not a cloud route. Website builds attendance from local store + live terminal logs. App builds it from member.attendanceDays + punches read from the machine.

2. APIs — what they fetch and what they update

Base /prod/.... Header X-Gym-Key required except OPTIONS. Institution from X-Institution or body/query, default Fitnessworld001.

Auth · Lambda auth · Cognito only, no Dynamo member read

MethodPathBehaviour
POST/auth/loginFetch Cognito token + staff role
POST/auth/forgotUpdate send reset code
POST/auth/confirm-forgotUpdate set new password

Members · Lambda members · user_profile (+ payment on pay)

MethodPathBehaviour
GET/membersFetch all members. Dynamo Query user_profile where institution = gym. Then, for up to 8 members whose Razorpay status is older than 90s, it also calls Razorpay. That extra step is a common slowdown. Returns mapped member JSON (toMember).
GET/members/{id}Fetch one. GetItem. If not found, Query all members and match id / enroll / phone. May call Razorpay to sync a pending subscription (syncPendingProfile).
POST/membersUpdate create member PutItem. CASH/UPI also PutItem payment (PAID). ONLINE: create Razorpay subscription, PutItem payment (PENDING), write pay link onto the member.
PUT/members/{id}Update existing PutItem. Pause/resume, extend due date, record CASH/UPI, send pay link. PATCH with recordAttendance:true merges attendanceDays on the member row (no separate attendance table).
DEL/members/{id}Update DeleteItem. First Query all members to find duplicates by id / memberCode / enroll. Attendance days on that row go away with the member. Machine punches are not deleted in Dynamo (they were never stored there).

Payments · Lambda payments · payment (+ user_profile on new link)

MethodPathBehaviour
GET/paymentsFetch all gym payments. Query GSI institution-paymentDate-index. If GSI missing: Scan whole payment table filtered by institution. ?memberId= uses Query on PK cognitoId instead (fast).
GET/payments/{id}Fetch one. Fast if ?memberId= (GetItem). Without memberId: loads all gym payments then finds the id. Slow.
POST/paymentsUpdate create Razorpay subscription + PutItem payment + update member pay-link fields.

4. Why responses feel slow

GET /members

1. Query every member for the gym (full items, including attendanceDays).
2. Collapse duplicates in Lambda.
3. Up to 8 Razorpay HTTP calls for stale subscriptions (90s cache).
This is the heaviest screen load (Members, dashboard, many app screens).

GET /payments without memberId — Query GSI of all payments, or Scan the whole table if GSI fails.

GET /payments/{id} without memberId — same full list, then find one row in memory.

GET /members/{id} miss — falls back to listing every member to search phone/enroll.

DELETE /members/{id} — lists every member to find duplicate enroll/id rows.

POST/PUT reports — lists every member and every payment to compute totals.

GET /members payload size — each member ships attendanceDays, attendance monthly map, pay links. Large gyms = large JSON over mobile networks.

Lambda: 256 MB, 20s timeout. Cold start + Query + Razorpay easily hits several seconds.

App also waits on LAN face-machine HTTP (connect, user list), separate from cloud time.

5. How to optimise response time

Do these first (biggest wins, least redesign):

  1. Confirm payment GSI exists in prod — name institution-paymentDate-index. If missing, GET /payments is a full table Scan every time. Create/fix the GSI so listPaymentsByIndex always succeeds. Then Scan never runs on the request path.
  2. Stop blocking GET /members on Razorpay — refreshStaleSubscriptionStatuses currently waits for up to 8 Razorpay fetches before returning the list. Return Dynamo members immediately. Refresh Razorpay in the background (webhook is already the source of truth for paid/renew).
  3. Require memberId on GET /payments/{id} — avoid listing the whole gym to find one receipt.
  4. Projection / slim list — GET /members?lite=1 should return id, name, phone, plan, due, status, enroll — not attendanceDays maps. Profile screen can GET /members/{id}.
  5. Cache gym lists briefly — CloudFront or API Gateway cache GET /plans and GET /settings (they change rarely) for 30–60s. Members maybe 5–10s with cache-control.
  1. Raise Lambda memory to 512–1024 MB — faster CPU for JSON mapping; often cheaper and quicker than 256 MB.
  2. Delete-member should GetItem first, not list everyone. Query begins_with / GSI on deviceEnrollId instead of loading all rows.
  3. Attendance — keep storing days on the member item for “THIS MO” counts. Do not add a scanned attendance table unless you Query by memberId+day. A new table only helps if PK is memberId (or enroll) and SK is timestamp.
  4. Client — app already has an 18s cloud timeout + one retry. Do not refetch members+payments+plans+reports on every tab switch; keep GymContext cache and refresh on pull-to-refresh / after save.
  5. Webhook — always put cognitoId + paymentId in Razorpay notes (already done on create). Then webhook is GetItem, never listPayments/Scan.

Later (nice-to-have): GSI on user_profile for deviceEnrollId and phoneNumber so lookup does not list the gym. Pagination on GET /members and GET /payments (LastEvaluatedKey). Move attendanceDays off the hot member item into SK att#YYYY-MM or a small attendance table keyed by cognitoId + day. Do not Scan. All payments for a gym → institution GSI. One member → PK cognitoId.

7. Institution

All gym rows are partitioned by institution = Fitnessworld001. Querying that partition is the correct way to get everything for this gym. Scan is the wrong way: it reads every gym’s data in the table, then filters.

8. How the face machine connects

The CardM / AI806 terminal is a local HTTP device on gym Wi-Fi. It is not in DynamoDB. The phone app talks to it directly: POST http://{machine-ip}/api. Cloud APIs are used for members, payments, and plans. The website used a gym-PC helper that queued commands as __devicecmd_* on user_profile; the phone app does not use that path for connect.

What staff do

  1. Put the face machine on the gym Wi-Fi (home screen on, not sleeping).
  2. Put the phone on the same Wi-Fi (laptop hotspot is fine if both devices join that hotspot). Same network does not mean the same IP — phone and machine each get their own last octet.
  3. Allow location / nearby Wi-Fi when Android asks. Reconnect asks again if permission was denied.
  4. Open the app → Terminal. The app reads the phone’s LAN IP, then looks for the machine by itself.
  5. If it was found before, it tries that saved IP first. Otherwise it scans the subnet.
  6. When found, it signs in with the machine web user/password stored in Terminal (default username admin). Connect / Scan Wi-Fi both run the same connect path. Staff do not need to tap Connect if the machine is already on the LAN.
  7. After login, the app loads people on the machine and pushes cloud members (name, enroll id, valid-until / days left).

Device IP stays empty until a live machine is found. Mobile IP is the phone’s address on that Wi-Fi.

What the app does (technical)

  1. Phone IP — expo-network reads the phone LAN address (example 192.168.137.126).
  2. Find the machine — GET http://{ip}/home.html (then /) and check the HTML for terminal marks. Hint IPs first (including last known host), then the rest of the /24, with a short timeout so scan cannot hang.
  3. Login — POST http://{ip}/api with cmd: login. If a saved IP fails, it scans, then logs in on the IP it found.
  4. Users / faces / logs — further /api commands (list users, add user, starttime/endtime, punch logs). Attendance days for “THIS MO” are stored on the member in user_profile; punches live on the machine.
  5. Offline — if the machine is down, member saves still go to cloud. Device writes queue on the phone and flush when Terminal connects again.

This LAN “Scan Wi-Fi” is not a DynamoDB Scan. Cloud Scan (if it happens) is only the payment table fallback described in section 3.

Will not connect if: phone and machine are on different Wi-Fi; Android LAN permission denied; machine is off the home screen; IP is from an old network and was not re-scanned.
